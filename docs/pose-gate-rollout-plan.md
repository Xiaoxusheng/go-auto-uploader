# 姿态门精度提升与正式上线执行方案

> 更新：2026-09-27。本文是后续操作的唯一清单：先完成本机灰度和定向标注，
> 再用全新的冻结集验收，最后才部署服务器。不要以已有冻结集 v2 的数字作为新的上线依据。
>
> 范围：生产运动高光链路后的姿态门 + 学习型 GBDT 门头（段级投票）。不改变运动模型的
> `highlight_*` 参数，也不把自动预标直接当作训练真值。

## 1. 当前基线（先记住，后续所有结果都与它比较）

| 项目 | 当前值 |
| --- | --- |
| 金标 | 429 片 / 16,265 个 8 秒窗；dance 6,580 窗，gesture 1,071 窗 |
| 三阈值生产门 | `vis=0.70` / `face=0.12` / `det=0.30` |
| 三阈值分组 CV | P=0.688 / R=0.913 / F1=0.784；五折均选中同一组参数 |
| 当前学习头 | `gate_head_v2_trees.json`，模型版本 `v3-flywheel3-20260927`，200 棵树 |
| 部署语义 | 生产门先产段；头在段内按 8 秒窗投票，`head_frac=0.5` 才保留 |
| 8080 状态 | 已灰度启用 `head_filter_enable=true`，48 小时观察中 |

冻结集 v2 的最近一次复测（开封 #8）是当前最可信的效果证据：

| 系统 | 窗级 P/R/F1 | 段级 P/R/F1 |
| --- | --- | --- |
| 仅生产门 | 0.560 / 0.959 / 0.707 | 0.125 / 0.500 / 0.200 |
| 生产门 + v3 头段级投票 | **0.700 / 0.959 / 0.809** | **0.250 / 0.500 / 0.333** |

结论：头已证明能减少误报，但还**不能正式全量上线**。上线瓶颈是最终段级，而不是窗级。

## 2. 正式上线验收线（不可降低，不可换口径）

必须在一个从未用于训练、调参或模型选择的**冻结集 v3**上，同时满足：

| 指标 | 通过线 | 当前 v2 参考值 | 尚需改善 |
| --- | ---: | ---: | ---: |
| 段级 Precision | >= 0.80 | 0.25 | +0.55 |
| 段级 Recall | >= 0.60 | 0.50 | +0.10 |
| 评估语义 | 固定为生产「门产段 ∧ 头段内投票」 | 同左 | 不得改成头独立分段器 |

补充上线条件：

1. 本机 8080 灰度连续观察满 48 小时，抽检未发现真舞被头误拒的系统性问题；
2. 冻结 v3 的 GT 在验收前不读取、不参与训练，也不据此调 `head_frac`、模型或三阈值；
3. 验收通过后，才按 `docs/POSE_GATE_SERVER_RUNBOOK.md` 部署到服务器；
4. 服务器部署后保留一键回退：`head_filter_enable=false`。

> 注意：冻结集 v2 已累计开封 8 次，只能保留作历史诊断，不能继续用于选择候选或宣称新的
> out-of-sample 成绩。

## 3. Phase 0：先稳定灰度实验（现在就做）

目标：让接下来收集的线上错误样本只反映 v3 头，不混入阈值自动变化。

- [ ] 记录当前配置快照：三阈值、`head_filter_enable`、`head_frac`、模型文件版本和时间。
- [ ] 灰度观察期内关闭 `auto_apply`；目前三阈值已在五折稳定，自动重定标不会带来有效收益，
  却会污染头模型的 A/B 结论。
- [ ] 保持 `vis=0.70 / face=0.12 / det=0.30 / head_frac=0.5` 不变。
- [ ] 每天从 `[POSE-GATE]` 日志抽检两类段：
  - 头投票拒绝的段：确认是否误杀真舞（Recall 风险）；
  - 门和头都保留的聊天/手势段：确认是否为残余误报（Precision 目标）。
- [ ] 观察满 48 小时后，汇总“误杀真舞段数 / 保留误报段数 / 总抽检段数 / 主播名”。

若发现真舞被连续误拒，立即关闭 `head_filter_enable`，保留日志和样本，回到仅三阈值门；
不要临时下调阈值或 `head_frac` 掩盖问题。

## 4. Phase 1：定向补金标（下一轮真正的提升来源）

不要继续扫 `vis/face/det` 网格：五折已经全部选中当前点，继续调参属于重复消耗。
每次做一批 **360 窗**，每片最多 8 窗，并限制同一主播占比，防止同一直播间的相邻窗刷满训练集。

建议每批配比：

| 样本来源 | 占比 | 目的 | 标注要求 |
| --- | ---: | --- | --- |
| 门通过且头也保留的聊天/gesture 段 | 50% | 找残余 FP，直接抬段级 Precision | 盲标 `dance` / `gesture` / `chat` / `closeup` / `none` |
| 门通过但头投票拒绝的段 | 25% | 发现并修复真舞误杀，保护 Recall | 同上，必须复核是否真舞 |
| 近阈值不确定带 + 随机对照 | 25% | 保留决策边界和总体分布 | 用 `hleval uncertainty-export` 导出候选 |

执行规则：

1. 新增的 gesture 样本优先来自**未出现过的主播**；目标至少覆盖 3 名主播、每人至少 60 个盲标窗。
2. 仅把盲标复核完成的样本并入 `gold_review.json`。自动预标与金标的二分类一致率只有
   79.7%，可用于候选排序，不能原样灌进训练集。
3. 保留每批的来源、主播、日期、标签分布和入库前后总数；训练、验证、冻结集严格按片切分。
4. 先补足一批再重训；不要每加入几十窗就重训一次。

## 5. Phase 2：训练与开发集筛选

每轮只比较“当前 v3 头”与“本轮候选头”，生产三阈值始终作为基线。训练前先写下本轮候选，
禁止训练后围绕开发指标反复改模型。

- [ ] 按**片**做 GroupKFold，绝不随机按窗切分。
- [ ] 额外做 leave-one-streamer-out：整名主播不进训练，测试它是否仍能降低误报。
- [ ] 同时输出窗级和段级，但仅以生产部署语义的段级指标决定候选去留。
- [ ] 候选必须同时满足：开发集段级 P/R 都不低于当前 v3，且无某一主播的 Recall 崩塌。
- [ ] 确定最多一个候选（含固定 `head_frac`）；候选确定后冻结，不再用 v2 改它。

若这一轮的目标仅是提升 Precision，则不能以牺牲 Recall 来换分：任一已验证舞主播出现
持续误杀时，候选直接淘汰。

## 6. Phase 3：建立并开封冻结集 v3

冻结集 v3 需要在候选模型与参数确定**之后**建立或至少完成标签封存，且素材/特征永久保护。

最低组成：

- [ ] 至少 3 名未参与本轮训练的新主播；
- [ ] 包含纯舞、手势聊天/轻晃、近景聊天、纯非舞四类内容；
- [ ] 每类保留可评估的连续段，尤其是手势聊天与真舞切换段；
- [ ] 源视频、1fps 帧、姿态特征、GT 和素材清单一起保存到保护目录；
- [ ] GT 做盲标后封存；验收脚本和生产段合并语义先固定。

验收时只运行一次候选与基线的对照。若未达到 §2 的 P>=0.80 且 R>=0.60：

- 不在 v3 上调参；
- 记录 FP/FN 的内容类型，回到 Phase 1 定向补样；
- 下轮重新建立新的冻结集 v4。

## 7. Phase 4：部署与观察

仅当 §2 和冻结 v3 全部通过后执行：

1. 依照 `docs/POSE_GATE_SERVER_RUNBOOK.md` 构建并部署 CGO 姿态门版；
2. 部署前确认服务器模型文件与本机验收模型一致（版本、校验值、特征顺序）；
3. 首次运行检查 `[POSE-GATE]` 日志，确认门和头均已加载；
4. 灰度首日继续按主播抽检保留段与拒绝段；
5. 任一明显舞区误杀，立即设 `head_filter_enable=false` 回退，仅保留三阈值门。

## 8. 明确不做的事

- 不再反复扫描三阈值；当前参数在按片五折中完全一致，收益近零。
- 不再基于已开封的冻结 v2 选模型、阈值或宣传新成绩。
- 不把自动预标直接加入金标训练集。
- 不把窗级 F1 当作上线依据；线上输出的是“段”，验收必须看段级 P/R。
- 不继续投入已证伪的 YOLO 姿态手工特征（位移、节拍、构形、可见性、脸部几何）。

若完成多轮定向金标后段级 Precision 仍明显低于 0.80，下一条值得投入的路线是语义视觉模型
（例如 CLIP）；前提仍是先满足“至少 3 名 gesture 主播、每人 >=60 个盲标窗”的数据条件。
