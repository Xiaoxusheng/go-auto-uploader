## 0. 先纠正一个前提

你说"通过训练提升准确率"。这句话里隐含一个前提：**现在有一个模型可以训**。实际不是。

当前系统是**无监督规则系统**：

```
YAVG(帧差) ─┐
            ├─ robustZ(中位数+MAD 自适应归一化) ─→ 加权求和 ─→ 固定阈值 1.5 切分
RMS(音频)  ─┘
```

它没有参数是"学"出来的，8 个参数（权重、阈值、时长、合并间隔…）全是经验值。
更要紧的是：**没有任何标注数据，所以"准确率"这个数字现在不存在**。
现在能说的只有"899 秒素材里检出的 07:28–10:10 看着像跳舞段"——这是主观判断，不是指标。

没有指标，任何"训练"都是盲调参：你不知道改完是变好还是变坏，也不知道该优化什么。

**所以正确的顺序是：**

```
Phase 0  能量化          ← 现在缺的是这个
Phase 1  修架构 + 加特征  ← 零训练成本，收益可能最大
Phase 2  学参数          ← 这才是通常说的"训练"
Phase 3  判别模型        ← 需要数据量支撑
Phase 4  数据闭环        ← 让系统越用越准
```

而且我要提醒一句：**"训练"很可能不是收益最大的那一步。** 下面 §1.2 列了三个结构性缺陷，
其中两个靠训练解决不了，得改架构。

## 1. 现状盘点

### 1.1 算法链路

| 环节 | 实现 | 关键参数 |
| --- | --- | --- |
| 特征提取 | `probe.go`：单次 ffmpeg 解码，视频 `fps=2,scale=160:90,tblend=difference,signalstats` 出 YAVG；音频 `aresample=8000,asetnsamples,astats` 出 RMS | 160x90 / 2fps / 8kHz |
| 归一化 | `score.go:robustZ`：`z = (x - median) / (1.4826 * MAD)`，MAD 塌陷时回退标准差 | SmoothWindow=5s |
| 融合 | 加权和，归一化到权重和 | Motion 0.8 / Audio 0.2 |
| 切分 | 阈值 → 链式合并（MergeGap）→ 丢短（MinDur）→ 限长（MaxDur，取最高分窗口）→ 补边（Pad）→ TopN | Threshold=1.5 |

**性能**：实测 5.7–6.7x 实时（899 秒素材跑 2m15s–2m36s），瓶颈在 H.264 解码，不在滤镜。

### 1.2 三个结构性缺陷（比调参重要得多）

#### 缺陷 A：单切片自适应归一化 → "整片跳舞"必然漏检

`robustZ` 的基线是**本切片自己的中位数**。如果某个切片整段都是跳舞：

```
切片内所有秒的运动量都高
→ 中位数也高
→ z 分全部接近 0
→ 永远到不了阈值 1.5
→ 报"整段都很平，未检出高光"
```

这不是参数问题，是**归一化方式的内生失效模式**。它只在"高光占切片比例较小"时有效
（899 秒素材里跳舞占 150/899 ≈ 17%，所以能检出 z=3.1）。
一旦切片边界正好把整支舞框住，或者主播整场都在跳，系统就瞎了。

线上日志里那串「未检出高光段（整段都很平）」有多少是待机、有多少是这种误判，
**现在分不出来** —— 因为没有标注。

#### 缺陷 B：音频权重方向可能是反的

从实测数据算一笔账（`out2.txt`，跳舞段 08:00 那一档）：

| 量 | 值 |
| --- | --- |
| 运动量 z | **3.13** |
| 音频 z | **−0.79** |
| 当前综合分 | `0.8×3.13 + 0.2×(−0.79)` = **2.35** |

跳舞时主播不说话 → 音频能量低于常态 → 音频 z 是**负的**。
当前 0.2 的权重在**扣分**，把 3.13 拉低到 2.35。

再看聊天段（00:30 那一档）：运动量 z ≈ −0.20，音频 z ≈ **+0.74**，
当前综合分 `0.8×(−0.20) + 0.2×0.74` = −0.01 —— 音频在**加分**，把聊天段往高光上推。

**两段合起来看：音频这一维的方向和"跳舞型高光"完全相反。**
把权重调成 0 或负值，跳舞段和聊天段的分离度立刻从 2.49 拉到 3.63（+46%）。

不过别急着改。这只是一条素材上的观察，负权重很可能是过拟合。
更可能的真相是：**RMS 作为"运动量"的负向代理，携带的是冗余信息，该换掉而不是调权。**
换什么见 §4.1（用语音活动率 ZCR 替代 RMS）。**该给什么权重，要靠标注 + 交叉验证定** ——
这正是"训练"的第一个真实用途。

#### 缺陷 C：2 维特征的天花板

| 场景 | 运动量能否识别 | 音频能否识别 |
| --- | --- | --- |
| 跳舞 / 大动作 | ✅ 强 | ❌ 负相关 |
| 唱歌 / 高音 | ⚠️ 弱 | ✅ 部分 |
| 游戏击杀 / 团战 | ❌ 几乎无 | ⚠️ 部分（音量突变） |
| 连麦互怼 / 语出惊人 | ❌ 无 | ⚠️ 部分 |
| 镜头切换（假运动） | ❌ 误判为高光 | — |

只有 2 个特征，且对"精彩瞬间"的语义几乎无感。**加特征是收益最大的单项改动**，
而且见 §1.3，成本几乎为零。

### 1.3 工程约束（决定模型能有多重）

| 约束 | 影响 |
| --- | --- |
| 服务端 **J1900 + 3G 内存（可用 ~2G）** | **禁止任何 CNN / 姿态估计 / 目标检测**。最轻的 MoveNet 也只有 0.5–2 FPS，15 分钟切片要跑 4–15 小时 |
| 已付一次全解码的代价 | **加特征几乎免费** —— 在同一条 ffmpeg 命令里多挂 metadata 输出即可，边际成本只是滤镜运算（160x90 上极便宜） |
| **推理成本 vs 特征成本差 6 个数量级** | 逻辑回归/GBDT 推理是**微秒级**，ffmpeg 解码是**分钟级**。所以"模型多大"根本不是约束，**特征提取才是** |
| 上传成功即删源文件 | ⚠️ **训练数据留不住**。`pipeline.go` 上传后 `os.Remove`，高光要等 3min+2min 才动手。**要攒数据必须单独处理**，见 §3.4 |

**结论**：能上的模型上限是「逻辑回归 / 小型 GBDT / 分段常数表」，全部可以纯 Go 部署、零依赖。
这不委屈 —— 在这个特征维度上，GBDT 和 CNN 的差距远小于"特征从 2 维到 20 维"的差距。

## 2. 目标与指标定义

先定义"准确率"到底是什么。分三层，从下往上越来越接近你真正在意的东西：

### 2.1 秒级指标（技术指标，用于训练）

把任务定义为**逐秒二分类**：这一秒是不是高光。

- `Precision = 检出的高光秒中真正是高光的比例`
- `Recall = 真正的高光秒中被检出的比例`
- `F1 = 2PR/(P+R)`
- 主要看 **F1**；但业务上 **Recall 更值钱**（漏掉一支舞比多剪一段废话更让人恼火）

### 2.2 段级指标（技术指标，用于验收）

- 检出段与标注段的 **IoU ≥ 0.5** 记为命中
- 段级 Precision / Recall / F1
- 这个指标比秒级更贴近"剪出来能不能用"

### 2.3 业务指标（真正的目标）

- **抽查通过率**：随机抽 20 个产出片段，人工判断"这段该不该发"，通过率
- **漏检率**：随机抽 20 个"未检出"的切片，人工看里面有没有明显高光
- **高光时长占比**：`产出总时长 / 原片总时长`。用于防止模型退化成"全选"
  （F1 很高的一个作弊解是"全都标成高光"，这个指标能立刻抓住）

### 2.4 反例基线（必须记录）

**任何新方案都要和"当前线上版本"在同一测试集上比。** 没有基线数字，
"提升了"就是空话。

## 3. Phase 0：让准确率可测量

> 目标：产出**一个数字**和**一套可复跑的评估命令**。不做训练。
> 这是整个方案的基石，跳过它后面全是空中楼阁。

### 3.1 标注格式

JSONL，一行一个切片，**秒级区间标注**（比段级标注便宜，且能算 IoU）：

```json
{"clip":"芙芙Nymph_2026-09-22_19-36-11_000.ts","streamer":"芙芙Nymph","scene":"dance","duration":899,
 "positive":[[450,600],[625,780]],
 "note":"450-600 跳舞；625-780 连麦唱歌；其余待机"}
```

字段说明：
- `scene`：`dance` / `chat` / `game` / `sing` / `idle` —— **必须分层**，
  "高光"的定义因场景而异，混在一起训出来的模型会四不像
- `positive`：高光区间列表（秒）
- 无高光就写 `"positive":[]`

### 3.2 评估工具（新增，约 300 行 Go）

放在 `cmd/hleval`，与主程序解耦，可独立跑：

```
hleval -labels labels.jsonl -clips <录像目录> [-ffmpeg <path>] [-cache <dir>]
       [-opts '{"threshold":1.5,"motion_weight":0.8}'] [-json out.json]
```

输出：
```
=== 秒级 ===   P 0.61  R 0.48  F1 0.54
=== 段级 ===   IoU@0.5 命中 7/12   段 P 0.58  R 0.47  F1 0.52
=== 占比 ===   产出 12.3%  标注 9.8%
--- 漏检清单（标注有、未检出）---
  芙芙Nymph_..._003.ts  425-610 (185s, scene=dance)  ← 峰值 z 0.42，疑似缺陷 A
--- 误检清单（检出、标注无）---
  芙芙Nymph_..._007.ts  120-190 (70s)  音频 z +1.8 / 运动 z -0.1  ← 疑似说话段
```

**关键设计**：漏检/误检清单要**带上各维度的 z 分**，这样每条错误都能直接归因到
"是缺陷 A / B / C 中的哪一个"，而不是只看一个数字。这是把指标变成改进方向的桥。

**必须有特征缓存**：`Probe` 跑一次 6.5x 实时，调参时要跑几十上百次，
不缓存的话一轮实验要几小时。缓存格式 = 每个切片的 `Series`（JSON 或二进制），
以切片路径 + mtime 为 key。

### 3.3 黄金测试集

| 项 | 要求 |
| --- | --- |
| 规模 | 20–30 个切片（约 5–8 小时素材） |
| 覆盖 | ≥ 5 个主播、≥ 3 种场景、**必须包含"整片跳舞"的切片**（专门验缺陷 A） |
| 划分 | 按**主播 + 日期**分组，禁止随机分切片（同场相邻切片高度相关 → 验证集泄漏 → 指标虚高） |
| 标注成本 | 1 小时素材约 15–25 分钟人工（看缩略图条 + 打区间） |

**标注工具不用做平台**。生成"每 10 秒一张缩略图拼成雪碧图 + 时间轴"的单个 HTML 页面，
鼠标拖选区间、导出 JSONL 就够。**80% 的时间会花在看视频上，不是花在界面上。**

### 3.4 ✅ 训练数据留存（已解决 2026-09-23）

`internal/uploader/pipeline.go` 上传成功后 `os.Remove(path)` + `os.Remove(originalTS)`。
高光要等 `highlightStableAge(3min) + highlightScanInterval(2min)` 才动手，**必然输给上传**。

三个方案，按推荐度排序：

1. **本地单独跑一个采集实例**（推荐）—— ✅ **已实施**：
   `D:/upload/_diag/live_train/`，独立 config + dataDir + save_path，端口 18080，
   `enableUpload=false`、**`watermark_enable=false`**（水印会污染 signalstats 特征）。
   配套 `start.bat`/`stop.bat`/`prune.py`（磁盘守护）/`collect.py`（批量提特征）/
   `pick_targets.py`（筛表演型主播）。名单 25 个（17 SOOP + 8 抖音舞蹈/才艺）。
2. **加一个 `keep_source_days` 配置**：线上保留 N 天源文件再删。简单但吃磁盘
   （线上 1080p 竖屏 360MB/15min，一晚几十 GB）。
3. **只在标注阶段拉取**：SSH 上去按需 `rsync` 未删除的切片。被动、不可靠。
   ⚠️ 2026-09-23 实测：**本机到 xyx.homes 的 SSH 当前不通**（IPv6 直连
   `Network is unreachable`，域名被代理 DNS 劫持成 fake-ip `198.18.0.12`），
   所以这条路线暂时不可用 —— 更说明方案 1 是对的。

## 4. Phase 1：特征与归一化升级（零训练成本）

> 这一步**不训练任何模型**，但可能是收益最大的一步。
> 它同时为 Phase 2/3 准备好特征。

### 4.1 特征扩展：2 维 → 18 维，成本几乎为零

关键洞察：**所有特征都在同一次 ffmpeg 解码里出**，只是多挂几条 filter 链。
899 秒素材现在跑 2m15s，加完这些预计 2m30s 以内（+10%）。

| # | 特征 | ffmpeg 出处 | 预期作用 |
| --- | --- | --- | --- |
| 1 | 运动量 YAVG（现有） | `tblend=difference,signalstats` | 基准信号 |
| 2 | 运动量·慢尺度（4s 窗口均值） | 同链后接 `metadata` + Go 侧滑窗 | 区分"持续跳舞" vs "单次跳一下" |
| 3 | 运动量·快尺度（0.5s 方差） | `fps=4` 独立链 | 动作频率，舞种区分 |
| 4 | **YDIF**（帧内像素差） | `signalstats` | 与 YAVG 互补，抗镜头平移 |
| 5 | **YMAX−YMIN**（画面动态范围） | `signalstats` | 舞台灯光变化 |
| 6 | **亮度变化率** | YAVG 的低频分量 | 灯光秀 / 游戏特效 |
| 7 | **scene_score**（镜头切换） | `select=gt(scene\,0.3),metadata=print:key=lavfi.scene_score` | ⭐ **排除假运动**（切镜头不是跳舞） |
| 8 | **freezedetect** | `freezedetect=n=-60dB:d=2` | ⭐ 直接判"画面冻结"（待机、卡顿） |
| 9 | RMS（现有） | `astats` | 基准音频信号 |
| 10 | **Zero_crossings_rate** | `astats` | ⭐ 语音活动代理，比 RMS 更接近"在说话" |
| 11 | **Flat_factor** | `astats` | 噪声/音乐 vs 人声 |
| 12 | **Peak_level** | `astats` | 突发音量（惊呼、爆点） |
| 13 | **Crest_factor** | `astats` | 动态范围，区分"持续 BGM" vs "人声断续" |
| 14 | **Noise_floor** | `astats` | 静音判定 |
| 15 | 静音率（RMS < 阈值的秒占比） | Go 侧统计 | 场景粗分类 |
| 16 | 音频-运动相关性（滑动窗口） | Go 侧 | 跳舞段典型为负 |
| 17 | 主播画像：历史运动量中位数 | 跨切片统计（见 4.2） | ⭐ 修复缺陷 A |
| 18 | 切片内时长 / 时间位置 | 元数据 | 边界效应修正 |

带 ⭐ 的 4 个是**优先级最高**的：它们直接对应 §1.2 的三个缺陷。

> **实现坑（务必注意）**：现在 `probe.go` 靠 `strings.Contains(line, "Parsed_metadata_")`
> 区分视频/音频路。**一旦挂多个 metadata 实例，ffmpeg 会输出
> `Parsed_metadata_0_`、`Parsed_metadata_1_`… 带序号**，而 `Parsed_metadata_0_`
> 同样 `Contains("Parsed_metadata_")` → **全部被误判成视频路，时间戳串台，静默出错**。
> 必须改成按 `Parsed_metadata_(\d+)_` 正则提取序号，建立 序号→特征名 的映射表。
> 这个坑很隐蔽：不会报错，只是分数悄悄变烂。

### 4.2 两级归一化：修复缺陷 A

把 `robustZ` 的基线从"本切片中位数"改成**收缩估计**：

```
baseline = α × median(本切片) + (1 − α) × median(该主播历史切片)
scale    = α × MAD(本切片)    + (1 − α) × MAD(该主播历史切片)
α = n / (n + k)          n = 本切片秒数, k ≈ 300（先验强度，用数据调）
```

- 新主播没有历史 → `α → 1`，自动回退到现在的行为（不破坏现有可用性）
- 老主播历史充足 → `α → 0`，基线稳定，**整片跳舞不再被判成"常态"**
- 历史基线用滚动统计存在 `data/highlight_baseline.json`，按主播维度

**另一个更简单的备选**：直接用**全局固定标度**（不做自适应）。
这依赖一个假设——不同主播的运动量绝对量级差异不大。现有素材显示中位数 6.87、
范围 1.03~33，**这个假设需要用 Phase 0 的黄金测试集验证**（多主播统计分布）。
如果成立，固定标度反而最稳（无状态、无冷启动、可复现）。**先测，再选。**

### 4.3 切片边界处理

切片是 `SegmentTime` 硬切的，一支舞可能横跨 2–3 个切片，被切成互不相连的段。

- 短期：`MaxPerClip` 从 3 提到 5，`Pad` 从 5 提到 8（边界段给足余量）
- 中期：分析时把**相邻切片的 Series 拼接**后再跑 Select，只在最后按切片边界回切。
  改动不大（`highlightPass` 里聚一下同主播同时段的切片即可），能直接消掉边界断裂。

## 5. Phase 2：学参数（这才是通常说的"训练"）

> 前提：Phase 0 完成（有标注 + 有指标）、Phase 1 完成（有特征）。
> 预计 3–5 天。

### 5.1 步骤一：超参搜索（最省力，先做这个）

8 个参数，目标函数 = 段级 F1（在验证集上）。

- 方法：**随机搜索**（200–500 次采样），比网格搜索高效得多；
  参数空间不大，不需要上贝叶斯优化
- 搜索空间：`MotionWeight ∈ [0,2]`、`AudioWeight ∈ [−1,1]`（**允许负值**，见缺陷 B）、
  `Threshold ∈ [0.5,4]`、`MinDur ∈ [5,30]`、`MergeGap ∈ [5,40]`…
- 因为 §3.2 有特征缓存，单次评估是**纯 Go 计算，毫秒级**，500 次搜索几分钟跑完

**这一步大概率就能拿到第一波明显提升**，而且产出的是可解释的结论
（"音频权重该是负的 / 该接近 0"），能直接反哺 §1.2 的判断。

### 5.2 步骤二：逻辑回归替换"固定权重"

现在的 `Score()` 是**手写死的线性组合**。换成学出来的：

```
logit = w₁·z(motion) + w₂·z(audio) + w₃·z(zcr) + … + b
p = sigmoid(logit)
高光 ⟺ p > 阈值
```

- 训练：scikit-learn `LogisticRegression`，几十行脚本
- **部署：导出成 Go 常量**，推理就是一次点积，纯 Go 零依赖，微秒级

```go
// 由训练脚本生成，勿手改
var modelV2 = Model{
    Weights: []float64{1.82, -0.11, 0.94, 0.63, ...},
    Bias:    -1.24,
    Features: []string{"motion_z", "audio_z", "zcr_z", "scene_z", ...},
}
```

**为什么先上逻辑回归**：特征只有 18 维、样本量几百到几千，
GBDT 会过拟合；而且线性模型系数**可以直接读**，一眼看出哪一维在起反作用
（就像现在发现音频权重该为负）。先拿到可解释的基线，再上非线性。

### 5.3 步骤三：时序后处理

逐秒分类结果会有毛刺（单秒跳变）。现在的 `Select` 已经在做合并/丢短，
但在**概率序列**上做会更自然：

- 中值滤波（窗口 5s）压毛刺
- 用 **HMM / Viterbi** 或简单的"最小段长约束"保证段的连续性
- 这一步通常能把段级 F1 再推 3–8 个点

## 6. Phase 3：判别模型（数据量够了再上）

> 前提：标注 ≥ 100 个切片（约 25–40 小时素材）。预计 1–2 周。

### 6.1 模型选择

| 模型 | 可行性 | 说明 |
| --- | --- | --- |
| **LightGBM** | ✅ **推荐** | 表格数据上通常最强；18 维特征正好是它的主场 |
| 逻辑回归 + 特征交叉 | ✅ 备选 | 加二阶交叉项，成本低 |
| 小型 MLP | ⚠️ | 收益/复杂度比不如 GBDT |
| 1D-CNN / TCN（时序） | ⚠️ 可选 | 只在 GBDT 到瓶颈后再试 |
| 视频 CNN / 姿态估计 | ❌ **禁止** | 服务端 J1900 + 2G，物理上跑不动 |

### 6.2 导出成纯 Go（关键工程点）

GBDT 部署有两种做法：

1. **导出树结构**（推荐）：LightGBM `dump_model()` → JSON → Go 里递归求值。
   每棵树几十个节点，推理是几十次比较，**微秒级**，零依赖。
2. **导出分段常数表**：把 18 维空间离散化后打表。简单但精度损失。

选 1。生成 `internal/highlight/model_gen.go`，训练脚本负责重新生成，
**Go 侧不引入任何 ML 库**。

### 6.3 训练流程要点

- **交叉验证必须按主播分组**（`GroupKFold`），否则指标虚高
- 特征标准化参数（均值/方差）要**一起导出**，否则线上/训练不一致
- **保留一个"永不参与训练"的测试集**，只在最后验收时用一次
- 记录每次实验：参数、数据版本、指标 —— 一个 CSV 就够，别上 MLflow

## 11. 实证结果（2026-09-23 实测）

方案写完当天就用真实素材把上面两个「猜测」验证了。所有数字可用
`tools/train_highlight/` 下的脚本复现。

### 11.1 素材与方法

- 主素材 `菜菜很忙-2026-09-22-15-48-48-003.mp4`（抖音竖屏 1080x1920 30fps，899 秒）。
  人工看图确认 **437–645 秒为跳舞**，其余为摆姿势/聊天/待机。
- 特征提取用本次新增的 `internal/highlight/features.go`：同一次解码拿到
  signalstats 27 列 + astats Overall 23 列，共 **50 列**，耗时与只取 2 个 key 基本一致
  （实测 8.81x 实时，瓶颈仍在 H.264 解码不在滤镜）。
- 关键实现点：**放开 `metadata=print` 的 key 过滤**，而不是多挂 filter 实例 ——
  后者会让 ffmpeg 输出带序号的 `Parsed_metadata_0_`，无法区分归属（见 §4.1 的坑）。

### 11.2 缺陷 A 已实证：整片跳舞必然漏检

| 归一化方式 | 跳舞段 z 峰值 | 超阈值秒数 | 检出段数 |
| --- | --- | --- | --- |
| 切片内自适应（**线上当前**） | 4.07 | — | 1 段（命中） |
| 切片内自适应，但**只取跳舞段当切片** | **2.27** | 7 | **0 段** |
| 改用全片基线归一化同一段 | 4.07 | 199 | 1 段 |

同一段舞，在全片里能检出，单独成片就完全检不出 —— 因为它的运动量中位数（21.41）
成了自己的基线，z 分被压平，7 秒超阈值够不到 15 秒的最小时长。
**换成「主播历史基线」后 z 分回到 4.07、199 秒超阈值、正常检出。**

### 11.3 缺陷 B 已实证：音频权重方向反了

用 AUC（尺度无关）而不是「分离度」比较 —— 后者会被权重缩放污染：
音频权重为负时 `(mw+aw)` 变小，分数被整体放大，看起来分离度暴涨，其实判别力没变。

| 运动权重 | 音频权重 | AUC |
| --- | --- | --- |
| 1.00 | 0.00 | **1.000** |
| 0.80 | 0.00 | **1.000** |
| 0.80 | **0.20（线上当前）** | 0.999 |
| 0.80 | −0.20 | 1.000 |
| **0.00** | **1.00（纯音频）** | **0.197** |

- 运动量**单独就能完美分离**（AUC = 1.000）；
- 加上 0.2 的音频权重反而**略微下降**；
- 音频单独使用时 AUC 只有 **0.197** —— 即「音频越高越不像高光」，方向完全相反。

**结论修正**：正确的调整不是「给音频负权重」，而是**把音频权重降到 0**。
它提供不了增量信息，只引入噪声。（单条素材的结论，但方向性证据很强：
0.197 离 0.5 极远，不是噪声波动。）

### 11.4 特征判别力排名（50 列，逐列 AUC）

| 判别力 | AUC | 特征 | 方向 |
| --- | --- | --- | --- |
| 0.989 | 0.989 | `v_YLOW` | 越高越高光 |
| 0.984 | 0.984 | `v_YAVG`（当前在用） | 越高越高光 |
| 0.983 | 0.983 | `v_VDIF` | 越高越高光 |
| 0.982 | 0.982 | `v_YDIF` | 越高越高光 |
| 0.982 | 0.982 | `v_VAVG` | 越高越高光 |
| … | | | |
| 0.727 | **0.273** | `a_RMS_difference` | 越高越**不**是 |
| 0.715 | **0.285** | `a_RMS_peak` | 越高越**不**是 |

**所有音频特征都排在末尾且方向相反。** 判别力最高的全是视频帧差统计量。
`v_YLOW`（帧差图像的低分位亮度）略优于当前在用的 `v_YAVG`。

| 配置 | P | R | F1 |
| --- | --- | --- | --- |
| baseline（切片内归一化 0.8/0.2 th1.5） | 1.000 | 0.923 | 0.960 |
| 先验归一化 + 仅运动量 th2.40 | 1.000 | 0.904 | 0.949 |

逻辑回归系数：`v_YLOW +2.84`、`v_YAVG +0.36`、`v_YDIF +0.32`、`v_VDIF +0.05`、
`a_RMS_level −0.78`。

**怎么读这组数字**：

- baseline 在这条素材上已经 F1 0.960 —— 因为「跳舞 vs 聊天」的运动量差异极大
  （中位 6.87 对 21.4，差 3 倍），**任务本身太简单，这条素材测不出模型的真正价值**。

- 音频系数第三次为负（−0.78）。**三条独立证据（AUC 排名、超参搜索、回归系数）
  都指向同一结论：音频权重应该降到 0。**

**这条素材测不到的东西**：缺陷 A 那种「整片都是高光」的场景（见 §11.2，已单独实证），
以及跨主播泛化（需要 15–20 个切片）。

### 11.5.2 三条可立刻落地的最小改动

基于以上实证，按「收益/风险」排序：

| 改动 | 位置 | 依据 | 风险 |
| --- | --- | --- | --- |
| 音频权重 0.2 → **0** | `config.json` 的 `highlight_audio_weight` | §11.3 + §11.5 三条证据 | 极低，改配置即可 |
| 归一化改为**先验基线** | `score.go:robustZ` | §11.2 实证 z 从 2.27 回到 4.07 | 中，需加基线存储与冷启动回退 |
| 主特征 `v_YAVG` → **`v_YLOW`** | `probe.go` 的 `:key=` 参数 | §11.5.1 系数 2.84 vs 0.36 | 低，但需重跑历史切片 |

第一条**改一行配置就能生效**，建议先做。第三条次之。第二条收益最大但要动代码。

`ablate_norm.py` 换成**真留一切片**（10 个标注切片、3875 行，每折留出一个完整切片，
且该主播不在训练折里 —— 最严格的冷启动设定）：

| 配置 | P | R | F1 |
| --- | --- | --- | --- |
| A 切片内归一化 + 线上 0.8/0.2 th1.5 | 0.879 | 0.437 | **0.584** |
| B 主播历史基线 + 线上权重 | 0.879 | 0.472 | 0.614 |

4. **逻辑回归泛化反而更差**（0.604，P 仅 0.495），且 `v_YLOW` 系数从 +2.84 翻成 **−0.22**

### 11.8 为什么基线必须按主播分（量级普查）

`survey_shorts.py`：10 个主播 58 条抖音**作品短视频**（每条 6–16 秒、已剪辑成品）。
⚠️ 这些**不进训练集** —— 与「长直播录像里找高光段」是不同分布。它们的正当用途是量级普查：

| 观察 | 数值 |
| --- | --- |
| 跨主播运动量中位数 | 10.24（芙芙Nymph）~ 20.87（睡觉踢被子），**2.04 倍** |
| 同一主播跨下载批次极差 | 小🐑睡了 6 个批次，极差/均值 **25.4%** |
| 跨主播波动 ÷ 主播内波动 | **4.1 倍** |

**结论**：基线要按**主播**分，不能按全体分 —— 全体中位数落在两个主播之间，
对低量级主播偏正、对高量级主播偏负，两边都错。但同一主播内部足够稳定，
所以「主播历史基线」在**有历史时**是可行且必要的（问题只在于多数主播没有历史，
见 §11.7 第 2 条）。

### 11.9 归一化方案对比：缺陷 A 修不动，阈值才是杠杆

既然 §11.7 证明「主播历史基线」在多数切片上不可用，这里只比**线上总能落地**的方案
（都只用当前切片 + 一份离线学好的全局统计量）。`norm_variants.py`，真留一切片，
每折的全局统计量只从训练折学，阈值在训练折上搜：

| 方案 | P | R | F1 | 折内阈值 |
| --- | --- | --- | --- | --- |
| **H 位置收缩** `α·med_s+(1-α)·med_g, mad_s` | 0.742 | 0.694 | **0.717** | 1.19±0.05 |
| I 位置用 25 分位 | 0.747 | 0.656 | 0.699 | 1.89±0.03 |
| A 切片内（现状） | 0.716 | 0.674 | 0.695 | 1.17±0.07 |
| B 主播历史基线 | 0.665 | 0.718 | 0.690 | 0.99±0.34 |
| F 全局位置 + 切片内尺度 | 0.524 | 0.446 | 0.482 | 1.34±0.13 |
| G 全局固定 | 0.459 | 0.434 | 0.447 | 0.86±0.07 |

**两个反直觉的结果，都值得记下来**：

1. **「全局位置 + 切片内尺度」（F）不但没修好缺陷 A，反而更差（0.482）。**
   原假设是：整片跳舞时 `med_s` 被抬高、`mad_s` 又小，z 被压平；换成低位的全局
   位置做分子即可恢复。实际败因在输出第一行 —— `med_g = 28.06` 是被 SOOP 切片
   拉高的，而 `caicai-003` 的常态只有 **7.0**：用全局位置给抖音切片定标，
   整条序列 z 全变负，直接漏光。**这恰好实证了 §11.8 的警告**：
   全体中位数落在两个主播之间，对低量级偏正、对高量级偏负，两边都错。
2. **最好的 H 也只比现状好 0.022（0.717 vs 0.695）。归一化不值得动。**
   投入产出比太低，还要改 `score.go` + 引入基线存储与冷启动回退。

**真正的杠杆是阈值**：A 方案在 th1.5 时 F1 只有 0.584（§11.7），th1.2 时 0.717
—— **同一个算法、同一份数据，只挪一个数字，+23%**。而且折内搜出的阈值在
H/A 两个方案上都高度稳定（1.19±0.05 / 1.17±0.07），说明 th≈1.2 是跨切片稳健的
最优区间，不是碰运气。

**逐切片明细（H 方案）暴露了任务本身的天花板**：

| 切片 | F1 | 说明 |
| --- | --- | --- |
| caicai-003 | 0.966 | 跳舞 vs 聊天，差异极大 → 简单 |
| dance-064016 | 0.886 | 同上 |
| dance-064128 | 0.737 | |
| dance-064057 | 0.686 | |
| gorani-10 | 0.673 | |
| dance-064023 | 0.586 | |
| dance-224903 | 0.532 | |
| gorani-2 | 0.493 | |
| dance-224222 | 0.419 | 1224 秒长切片，正样本仅占 8% → 误检多 |
| golani-2 | 0.349 | 整片都在表演 |

**垫底的都是「整片都在表演」的 SOOP 切片** —— 正是缺陷 A 的场景。但它们的标注本身
就是相对的（"这两段动作幅度最大"），**没有真正的「常态」参照**。也就是说：
这类素材上「高光」的可定义性本身就弱，**归一化换算法解决不了**，
只能靠采集更多「有聊天/待机间隔」的素材（§11.10）。

### 11.10 落地：只改三个数字

基于 §11.7 + §11.9，**已落地**的改动只有配置（零代码改动，风险极低）：

```json
"builtin": {
  "highlight_motion_weight": 1.0,
  "highlight_audio_weight": 0.0,
  "highlight_threshold": 1.2
}
```

| 参数 | 原值 | 新值 | 依据 |
| --- | --- | --- | --- |
| 音频权重 | 0.2 | **0** | §11.3 三条独立证据（AUC 排名 / 超参搜索 / 回归系数）+ §11.7 |
| 运动量权重 | 0.8 | **1.0** | §11.7 落地候选对比 |
| 阈值 | 1.5 | **1.2** | §11.9 折内阈值 1.19±0.05，且 F1 峰值在此 |

预期 F1 **0.584 → 0.717（+23%）**。

⚠️ **`highlight_motion_weight` 与 `highlight_audio_weight` 必须同时给**：
`applyDefaults` 的回落条件是「两者**同时**为 0」，只写 `audio_weight: 0`
而漏写 `motion_weight` 会被静默改回 `0.8/0.2`。
`internal/config/highlight_params_test.go` 已把这个契约钉住。

### 11.11 采集素材实测：三个新发现（含一个新缺陷）

本机采集实例（§3.4）录下的头 8 个切片，逐个看图后**没有一个能直接用于训练**，
但原因各不相同 —— 这本身就是有价值的信息。

| 切片 | 时长 | 看图结论 | 问题类型 |
| --- | --- | --- | --- |
| 梦梦m | 163s | 候选段和常态段**都在挥绸带跳舞** | 全程表演型，无高光/常态边界 |
| Miller 米乐 | 127/195s | 画面是**多画面叠加 + 横屏** | 在放横屏素材，非真人实时直播 |
| 아란 | 131s | z 峰值 **17.46**，画面是游戏菜单切页 | 场景切换被误判成高光 |
| 笛笛畏 | 16/106s | 反复断流（`exit status 0xcfcfcb08`），每次只录 5 秒 | 该主播的流有问题 |
| 燃燃 / 其余 | 73s | 太短，常态样本不足 | — |

#### ⚠️ 新缺陷 D：纯运动量把「场景切换」误判成高光

`아란` 那条切片里运动量 z 峰值 **17.46** —— 比真实跳舞段（caicai-003 的 4.07）
**高出 4 倍多**，而画面只是「游戏菜单 → 游戏内画面」的切页。

原因很直接：帧差统计量度量的是「画面变了多少」，切页/切场景会让**整屏像素同时改变**，
幅度远超任何真实肢体动作。**当前算法对此毫无抵抗力。**

**这不是采集问题，是算法缺陷**，且之前用 D 盘素材时没暴露（那些都是单一场景）。

#### 取证：两种简单修法都被实测否掉了

`scene_switch_probe.py`（新增）在**同一素材内部**对比「异常时刻 z>8」与「普通时刻
0.5<z<2」，避免混入「游戏画面 vs 真人画面」的场景差异。

**① 找不到有判别力的现成列。** 逐列比对 50 列，最强的候选是 `v_YHIGH`：

| 素材 | v_YHIGH 高段 | v_YHIGH 普通 | 比值 |
| --- | --- | --- | --- |
| caicai-003 真实跳舞 | 75.25 | 34.50 | 2.18 |
| 아란 游戏切页 | 5.00 | 1.00 | 5.00 |

两组**都是「高段 > 普通」**，只是绝对量级差 10 倍 —— `v_YHIGH` 只是跟着运动量一起
放大，**没有判别力**。根因：现有特征都是对整图算的**全局标量**，把「整屏变化」与
「局部变化」的空间差异抹平了。

（曾设想用 `v_YLOW/v_YAVG` 当「均匀度」指标 —— 局部变化时低分位被静止区域拉低、
比值 < 1。实测**恒为 0**：`scale=160:90` 后静止像素占比永远 ≥10%，低分位必然是 0。
假设不成立。）

**② 中值滤波压不住。** 原以为切页是 1~2 秒的针状尖峰，实测是**持续十几秒的段**
（菜单停留/加载画面）：

| 素材 | 原 z 峰值 | 中值 k=3 | k=5 | k=9 |
| --- | --- | --- | --- | --- |
| 아란 游戏切页 | 17.46 | 16.35 | 15.77 | **14.02** |
| caicai 真实跳舞 | 4.07 | 3.88 | 3.79 | 3.52 |

滤波后仍高达 14.02，**几乎没压下去**。所以「要求高 z 持续多秒」这条也无效 ——
它本来就是持续的。

#### 剩下的可行方向（未验证，不建议先动主链路）

真正对症的是**空间信息**：场景切换是**所有块同时变**，真实动作只有**部分块变**。
要做分块统计，必须先修 `probe.go` / `features.go` 的解析 —— 按
`Parsed_metadata_(\d+)_` 提取实例序号建映射表，才能安全地多挂 filter 实例
（现在用 `Contains("Parsed_metadata_")` 判断，一旦多实例就会把音频路也判成视频路、
静默串台，见 §4.1 的坑）。这是中等改动，收益未验证。

**成本更低的替代**：采集侧直接排除游戏直播类主播（见下方策略修正）。

#### 自动筛选判据的局限（诚实记录）

`screen_clips.py` 首版用 `p90/median` 当自动判据，**判错了两类**：

- `梦梦m` 对比度 2.17 被判「可用」，但它是全程表演型 ——
  `p90/median` 分不出「动作幅度有快慢」和「状态切换」。
- `아란` 的 z=17.46 尖峰**没被抓到**，阈值定太严（游戏画面本身一直在动，
  邻域不满足「安静」）。

所以该脚本已降级为**参考指标展示**，不再输出「可用/不可用」判定。
**定性只能靠看图**（`label_assist.py` 抽的拼图）。

#### 对采集策略的修正

采集名单应排除三类：

1. **游戏直播** —— 界面切换污染特征（`아란` 就是）
2. **放横屏素材 / 多画面型** —— `Miller`
3. **全程表演型** —— 无常态参照，缺陷 A 场景（`梦梦m`、SOOP 系列）

只保留**有聊天/待机间隔的真人才艺主播**，即 `caicai-003` 那种
「437–645 秒跳舞、其余摆姿势/聊天」的形态。
